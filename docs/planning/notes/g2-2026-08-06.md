## tool-catalog function used

No single `invokeTool()` exists in tool-catalog.ts. G2 built `dispatchViaToolCatalog()` in skill-dispatch.ts that:
1. Dynamically imports `TOOL_CATALOG` from `./tool-catalog.js`
2. Maps skill names (hyphens) to tool names (underscores): `wi-search → wi_search`
3. Finds the tool definition and calls `tool.handler(args, toolContext)` directly
4. Wraps in `Promise.race` with per-skill timeout

Skills with DIRECT tool-catalog handlers (no runSkillSubagent recursion):
- `wi_search` → calls `searchMessages()` in-process
- `wi_search_all` → calls `searchAll()` in-process

All other wi_* handlers call `runSkillSubagent` → would recurse → skipped via `DIRECT_CATALOG_SKILLS` set → HTTP path used.

## dispatch function

`runSkillSubagent(skillName, args, ctx)` — same export as before. Flow:
1. Write `pending` audit row
2. Look up route in SKILL_ROUTES
3. CLI-only → `failed` (no change from pre-G2)
4. If `DIRECT_CATALOG_SKILLS.has(skillName)` → call tool-catalog handler in-process
5. Otherwise → HTTP fetch to bridge endpoint with `Promise.race(timeout)` + retry x2
6. On retry exhaustion → DLQ row written

## Known limitations

- Dev bridge can't boot (duplicate column `source_id` migration + missing `cypher-sessions.js`). These are pre-existing infra issues (G3/wave-A scope). G2 tested via in-memory DB import.
- Only 2 skills use tool-catalog direct path. Remaining 17 wi_* handlers call back to `runSkillSubagent` — would cause recursion if invoked via tool-catalog. Kept HTTP for those.
- No `palace` or `user` on `SkillDispatchContext` — tool-catalog handlers that need these (none currently) would fail. Extending `SkillDispatchContext` with optional `user`/`palace` fields is future work.
